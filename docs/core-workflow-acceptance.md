## Confirmed defects addressed

The browser already blocked review until the current photograph loaded, but the assignment API previously forwarded approve/complete directly to the RPC without checking Storage. A local test reproduced HTTP 200 despite an unreadable photo. The route now checks caller dispatcher membership before reading bytes, selects finalized evidence belonging to the assignment's current round, downloads it with the caller's session, checks length/SHA-256, and only then invokes the existing RPC. Missing/throwing reads and corrupt bytes stop the transition and return safe retry guidance; raw service details are not exposed. Anonymous, hidden-assignment and verifier cases stop before the photo read.

The report previously omitted consented coordinates and showed a timestamp without making its meaning clear. It now pairs each submission with the original question/requested location, verifier observation, photograph, explicitly labelled submission time, optional coordinates/limitations, and that evidence's review outcome/time/note. Text is escaped by React. No timestamp, authenticity or human review is fabricated.

Existing staged fixes retain form data, reuse pending evidence IDs/consent, distinguish saved writes from failed refreshes, suppress stale account/read responses, handle Storage failures without false submission, verify private proxy bytes and prevent UI review of an unloaded photo. Upload success alone never signs/finalizes. SQL row locks and existing exact-retry rules prevent duplicate finalization/completion events. A byte check and a database transaction are separate operations; they are not an atomic Storage transaction or proof of human judgment. The direct RPC still enforces its existing database invariants; no new database policy is claimed.
